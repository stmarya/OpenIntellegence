# P2–P6 runtime slice

This document records what is implemented in code and what remains a runtime verification item. A committed component is not described as healthy until its CI and dev-stack execution have been observed.

## P2 — service identity and API keys

- `python -m app.cli.bootstrap_tenant --slug <slug> --name <name>` creates the first tenant and prints one privileged key exactly once.
- Bootstrap fails closed when the tenant already has a key. Later keys use the authenticated `/api-keys` API.
- The console reads through a server-only `API_SERVICE_KEY`. It is never compiled into browser JavaScript.
- Write requests require an additional `CONSOLE_ACTION_TOKEN`, same-origin validation, and an allowlisted operation. This token is not an API key and must not be reused elsewhere.

## P3 — endpoint agent

`endpoint_agent/client.py` is one cross-platform Python entry point for Windows, Linux, and macOS. It:

1. generates a 3072-bit RSA private key and CSR on the endpoint;
2. exchanges a single-use enrollment key for an mTLS certificate;
3. stores key material with owner-only permissions where the OS permits;
4. reports heartbeat and bounded software inventory;
5. opens no listener and has no arbitrary shell action.

Endpoint intent delivery remains deliberately approval-only. The client does not poll or execute commands until a per-agent, replay-resistant verification design replaces the current server-only command-envelope prototype.

## P4 — grounded AI

Model prose is accepted only when it contains citation markers that resolve to retrieved evidence. Missing or out-of-range markers cause the narrative to be withheld while keeping the retrieved sources visible. Provider response bodies are not returned to API callers. Report failures record only the exception class, not prompts or provider payloads.

## P5 — workers and connector delivery

The default compose stack now supervises:

- connector delivery;
- internal case/report queue handling;
- alert evaluation;
- endpoint-intent expiry.

OpenSearch and MinIO moved behind the `extended` profile because no application adapter consumes them yet. A configured dependency is not reported as healthy merely because its container started.

## P6 — write workbench

`/actions` exposes eight explicit operations through a same-origin server route: create case, investigation, alert rule, API key, report, and endpoint intent; acknowledge an alert; and trigger one connector ingest. The route cannot proxy arbitrary paths. Endpoint actions create approval-controlled intent only; they do not claim device delivery.

## Before starting dev

```bash
cp .env.example .env
python -m app.agent_gateway.bootstrap_ca --out ./certs
# Set API_SERVICE_KEY and a different CONSOLE_ACTION_TOKEN in .env
docker compose up --build
```

The frontend lockfile is still generated by an actual npm install and must be committed before switching CI and Docker builds from `npm install` to `npm ci`.
